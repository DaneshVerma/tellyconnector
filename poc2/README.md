# TallyPrime → Cloud HTTP Proof of Concept

This project is intentionally small. It proves whether a TallyPrime instance running on a local Windows machine can send an outbound HTTP/HTTPS request to a cloud API we control, without installing a custom connector, service, or inbound port-forwarding on the user's machine.

The app runs a FastAPI service that accepts a raw POST body, logs headers and content type, and exposes a webpage to inspect the latest request.

## What this experiment tests

Local:

TallyPrime → public FastAPI URL

The result proves that the client machine can initiate outbound traffic to the internet, and that a public HTTPS endpoint can receive it. This is a one-way proof from the local machine to the cloud. It does not by itself prove full bidirectional synchronization or that TallyPrime can receive data back from the server.

## Project structure

- `app.py` – FastAPI app with webhook endpoint, latest-request inspector, and health endpoint
- `requirements.txt` – Python dependencies
- `Dockerfile` – container definition for deployment
- `render.yaml` – Render deployment config

## Endpoints

- `GET /health` – health check
- `POST /api/tally/webhook` – receives the Tally request body and logs it
- `GET /api/tally/latest` – returns the latest request metadata as JSON
- `GET /` – simple inspector page

## Run locally

1. Create and activate a virtual environment (optional but recommended):

   ```bash
   python -m venv .venv
   source .venv/bin/activate
   ```

   On Windows PowerShell:

   ```powershell
   py -3.11 -m venv .venv
   .\.venv\Scripts\Activate.ps1
   ```

2. Install dependencies:

   ```bash
   pip install -r requirements.txt
   ```

3. Start the app:

   ```bash
   uvicorn app:app --host 0.0.0.0 --port 8000
   ```

4. Visit:

   - http://localhost:8000/health
   - http://localhost:8000/

## Simulate a Tally request locally

```bash
curl -i -X POST "http://localhost:8000/api/tally/webhook" \
  -H "Content-Type: text/xml; charset=utf-8" \
  -H "User-Agent: TallyPrime-Test/1.0" \
  --data-binary '<TALLYREQUEST><Party><Name>Example</Name></Party></TALLYREQUEST>'
```

Expected result: the app logs the headers, content type, and raw XML body, and returns a JSON success response.

## Deploy to Render

1. Push this project to a GitHub repository.
2. In Render, create a new Web Service and connect the repository.
3. Use the included `render.yaml` and `Dockerfile`.
4. Render will build and expose the app over HTTPS.
5. Set the public URL generated by Render, for example:

   `https://your-app-name.onrender.com`

6. Use that URL in the TallyPrime HTTP call.

## Example public URL

The TallyPrime HTTP action must point to a public endpoint such as:

```text
https://your-app-name.onrender.com/api/tally/webhook
```

## TallyPrime request template

The exact command names and parameters differ by TallyPrime version. The important part is not the literal syntax here; it is the documented HTTP request action in TallyPrime, configured to POST to your public URL.

Use the HTTP/REST/TDL integration method documented in your TallyPrime version and adapt the fields below to match that version's exact names.

```text
# TEMPLATE ONLY — adapt the field names and command names to your TallyPrime version.
# This is not a guaranteed literal TDL program.

[HTTP POST Action]
  URL: "https://your-app-name.onrender.com/api/tally/webhook"
  Method: POST
  Content-Type: text/xml
  Body:
    <TALLYREQUEST>
      <Party>
        <Name>Example</Name>
      </Party>
    </TALLYREQUEST>
```

Important adaptations you may need to make:

- exact HTTP action name or function name
- field names such as URL, Method, Content-Type, or Body
- how the TDL expression writes the XML payload
- whether your version expects a text/xml, application/xml, or a different header

The proof-of-concept only requires a standard outbound POST request to the cloud URL.

## Logging behaviour

The app logs the following for each request:

- request received
- headers
- content type
- raw body
- response returned

This is printed to the console in the server logs and can be inspected in the hosting provider logs as well.

## What this proves

This POC proves that:

- TallyPrime can initiate an outbound HTTP POST from a local Windows machine to a public cloud API
- no inbound connection to the user's local machine is required
- a cloud-hosted FastAPI service can receive and log the payload

## What this does not prove

This POC does not prove:

- bidirectional synchronization is available from the server back to TallyPrime
- TallyPrime is able to receive or process any callback from the cloud
- authentication, retries, secure encryption, or production reliability have been implemented
- the server can trigger actions on the local machine or push data back without a separate mechanism

This is only a one-way connectivity check: TallyPrime -> cloud.
